## 3. 当前状态和工作重心

### Claude 建议

把工作重心从从零训练小模型转向冻结预训练模型；认证构造独立推进，不应阻塞预训练模型插入。

### Codex 判断

该优先级合理，但“宿主模型没有真实能力”不准确。项目已有具备实际分类能力的 ResNet，E2-A/B 也已取得受控记忆结果。尚未取得充分证据的是当前小型 Transformer 在目标自然语言任务上的稳定效用和泛化。

工作日志中 E2-C 的 Plain/CAN 在未见模板上均退化；T2 CAP/C0 单 seed、每 scope 4 个 dev 样本的 NO-GO，只能说明当前配置不适宜冻结，不足以判定 Gate 导致退化，也不能证明小规模从零训练不可能产生语义泛化。

C-006 是已经记录的 CIFAR 能力分级结果；C-016 是待验证的 Transformer 能力分级主张。不能因 T2 未闭合而否定 C-006，也不能用 C-006 替代 C-016。

toy 关系阻塞的是密码学不可伪造性等主张，不否定条件性命题：“当 verifier 拒绝时，受保护分支是否零调用”。

**建议采用表述**：

> 近期优先闭合冻结预训练宿主上的 Gate 插入与执行隔离；精确认证构造独立推进。两类工作在研究问题上可分离，但最终组合仍需共同验证精度、接口和执行行为。

## 4. 当前实数关系与最小二乘缺陷

### Claude 建议

当前 A 从实数正态分布采样，没有 mod q；缺陷属于关系结构，不是简单参数太小。“一行 lstsq 必然通过”，调参数不能修复。

### Codex 判断

结构性缺陷判断正确。当前 verifier 接受浮点向量，只检查残差，不要求输入属于生成时的小整数秘密集合。

在精确算术下：

```text
min_c ||A c - b||₂ <= ||A s - b||₂
```

只要原秘密 s 满足当前阈值，最小二乘最优解也满足该残差阈值。因此，仅调整维度、噪声或阈值，同时维持这种不受限实数残差验证结构，不能建立所需的秘密持有认证安全。

但“必然成功”应带条件：数值求解及输入转换有误差；原生成秘密也可能不满足阈值。Claude 给出的约 11.3 是特定高斯和秩条件下的典型残差量级，不是每次实例的确定值。代码行数也不等于算法复杂度 O(1)。

本结论是解析判断，未运行恢复代码，不报告新的成功率。

## 5. mod-q 候选、安全估计与神经精确性

### 5.1 Claude 提出的候选

```text
A ∈ Z_q^(m×n)
s 为小范数秘密
b = (A s + e) mod q
r = centered_lift((b - A c) mod q)
接受条件：||r||∞ <= β

候选：q=3329，n=256，m=512，s_i ∈ {-2,-1,0,1,2}
```

Claude 建议以精确神经算术、reference 差分和 lattice-estimator 报告作为 G1 首轮范围。

### 5.2 Codex 对安全性的判断

该关系可作为独立研究候选，但不能直接宣称“加 mod q 就获得 search-LWE/BDD 认证安全”，也不是唯一可能的升级路线。

必须补充：

- 输入 c 的整数性、规范编码、系数范围检查；
- A、s、e 的准确分布、样本数及参数；
- 阈值 β 与错误拒绝率、可接受替代解集合之间的关系；
- 恢复原秘密与寻找任意可接受凭据的区别；
- 自适应验证查询、公开反馈和多次使用的访问模型；
- relation correctness、秘密搜索难度与完整协议安全之间的论证。

若生成小整数 s，而验证器仍允许任意浮点 c，则研究对象已不再是声明的离散凭据域。

Kyber 使用 q=3329，不意味着此普通 LWE 实例具有 Kyber-512 的安全强度；其维度和 Module-LWE 结构不能直接移植。lattice-estimator 的结论依赖输入分布和攻击模型，只是已建模攻击的成本估计，不能替代协议证明。

每次请求直接提交 s 的机制仍是静态持有者凭据检查，不是数字签名。观察到完整秘密后可在其有效期间复用；泄露、撤销与新鲜性需要另行处理。

### 5.3 Codex 对 FP32 精确性的判断

Claude 计算的乘加绝对上界正确：

```text
256 × 3328 × 2 = 1,703,936 < 2^24
```

在规范小整数输入、适当算术实现下，这有助于证明部分乘加精确。但是完整证明还需覆盖：

- b 的减法及所有后续中间值；
- 除法或倒数乘法的舍入；
- floor、模约简及 centered lift 的边界；
- ReLU 构造的权重精度、中间值上界及消减；
- TF32、autocast、编译器和设备后端；
- 超出规范域输入的确定性拒绝。

“输入为整数，所以 floor(x/q) 精确”不是充分证明。即使有限域上的具体实现可以证明精确，也必须给出该实现的论证。

有限整数域上的 floor/比较可由分段线性网络表示，但有限 ReLU 网络不能在整个连续实数域上精确表示不连续函数。应同时说明域约束、网络宽深度、算子数和运行成本。

较大模数也不必然要求整条链使用 float64/int64；分块表示、分段累加和中间约简是候选实现方式。

**采纳方式**：G1 首轮可收窄为一个关系内核；q=3329 保留为候选，安全级别和全链精确性均标为待验证，不直接冻结。

## 6. 硬门控、mod-q 与业务训练

### Claude 原论断

> “上了更强的门，就永久回不去端到端训练。”

### Codex 判断

该论断错误，混淆了对 credential 的可微性与对业务特征的可微性。

对于固定凭据：

```text
g = V(c) ∈ {0,1}
h' = g h
∂h'/∂h = g I
```

合法样本仍可以更新共享前缀及后缀。条件分支也可以对实际执行的路径反向传播，不需要对离散授权选择本身求导。

因此：

- 固定精确 verifier 可以与业务网络训练共存；
- 不必学习 verifier 权重；
- 硬路由不要求永久冻结业务骨干；
- 软 surrogate 可以作为训练实验，但不能以其近似正确性承担精确认证保证；
- 若 soft surrogate 允许未授权样本执行深层，则该训练实验不具备推理阶段的 zero-call 属性，必须分开描述。

首轮采用“固定认证、冻结骨干、只训公共读出”仍然合理，原因是保持原模型行为和减少变量，而非数学上无法联合训练。

**采纳方式**：首轮使用硬路由，认证模式与 model.train() 解耦；不接受“不可逆、永久禁止联合训练”。

## 7. 预训练模型插入建议逐项核查

| Claude 建议或说法 | Codex 判断与建议 |
|---|---|
| 合法路径直接传 hidden，不缩放 | 采纳。减少不必要运算，但分组和后端差异仍需数值验证，结构恒等不自动保证跨运行配置逐比特一致 |
| 先分组再运行 suffix | 采纳。实际条件执行才能支持 zero-call；不只存在 index_select 一种合法实现 |
| 共享输出头可能改动 embedding | 正确。冻结共享参数并审查 optimizer；训练后核对原权重及重跑 P1 |
| 只能 deepcopy/clone 输出头 | 过强。冻结共享输出投影、只训练独立 adapter 同样可行 |
| 无训练截断必然乱码 | 不成立。可能退化，也可能部分可用；应保留实测基线，不预设负向结果 |
| 原 RMSNorm 校准了最后层固定统计 | 不准确。RMSNorm 按当前输入归一化；中间表示与最终表示仍可能不匹配 |

| P1 不需要数据协议或效用检查 | 不准确。不需训练语料，但需固定评估输入与覆盖范围，并验证原宿主会做目标任务 |
| P1 单独形成可发布里程碑 | 采纳为独立可验收、可报告里程碑；不承诺单独足以发表论文 |

建议在模型选择时核查实际 tie_word_embeddings、权重共享引用和版本，不把尚未读取的候选 config 当作已验证事实。

P1 最低应有两个分离对照：“原模型 vs 恒等切分模型”“恒等切分模型 vs 合法 credential 路由”。P2 后再次执行这两个对照，并核对原骨干权重完整性。

## 8. 外部验证器对照与论文定位

### Claude 原论断

> “外部 verifier 做不到这一点（它要么放行要么拒绝，要么得跑第二个模型）。”

### Codex 判断

该论断错误。外部 verifier 同样可以控制一个共享骨干的分支：

```text
外部 verifier -> 已提交权限
                      |
输入 -> 共享 prefix --+--> public head
                      +--> protected suffix
```

它可以提供公共服务、保持共享参数，并实现未授权 suffix 零调用，不需要第二个独立模型。

因此，必须区分两项因素：验证器位置与模型共享方式。

| 对照 | 验证位置 | 模型组织 | 作用 |
|---|---|---|---|
| 原完整模型 | 无 | 完整骨干 | 原始业务效用参考 |
| 外部 verifier + 共享分支模型 | 模型外 | 同一 prefix/public head/suffix | 神经验签位置的关键强对照 |
| 模型内 verifier + 共享分支模型 | 模型内 | 与上一组相同 | 检验编译、部署及性能差异 |
| 外部 verifier + 独立大小模型 | 模型外 | 两套骨干 | 可选，检验模型共享收益，不能归因于验证位置 |

各验证对照应尽量使用相同认证关系、参数、权限策略和 dispatcher。外部验证可以更早拒绝并节省 prefix，需单独计入。

“外部 verifier 更安全”也需要实现与威胁模型依据，不能自动成立。能力分级既可以是产品需求，也可以涉及访问控制安全，不宜简单断言它不是安全需求。

建议保留 credential-conditioned capability tiering with in-graph verification 作为候选论文表述；最终投稿方向取决于实际证据。共享子网络符合用户架构目标，但不能单独构成神经验签独有的创新。安全假设和边界应在问题定义及方法中说明，不能只放在 limitation。

## 9. 成本估计、ML-DSA 与后续范围

### 9.1 训练与资源

单卡复现大规模语言模型预训练不适合作为当前主线，采纳此范围控制。Claude 用 6ND 计算的量级不能直接证明所有“从零重训带 Gate 模型”都不可行；具体语料规模和有效算力需另行核实。现有负向实验也不支持“小规模训练不可能获得语义泛化”。

G1 的 CPU 原型可与 GPU 宿主实验独立推进，但完整神经构造的宽深度、证明成本和部署性能未知。GPU 精度与吞吐验收仍需目标硬件。不得预先承诺“零 GPU 成本”或 P1 必定 1–2 天完成。

### 9.2 ML-DSA

暂不进行完整 ML-DSA 神经化是合理的首轮范围选择，但哈希或解析并非原则上无法电路化/神经表示。固定长度或有界域上的构造可研究，关键是规模、效率、算子支持及证明成本。

Claude 的操作计数未给出来源；“拒绝采样”需要区分签名阶段的拒绝循环与验证端公共矩阵展开等采样，不能混写。论文贡献可定位到允许算子集、精确域和资源边界，但不能在无证明时宣称某类算子无法神经化。

### 9.3 Replay 与凭据泄露

无状态前馈层无法独立记忆已消费请求，正确。系统级新鲜性可通过挑战、nonce、请求绑定和状态管理另行设计；是否使用哈希及如何实现取决于协议，不应因此宣布 replay 在系统层永久不可研究。

直接发送秘密向量属于 bearer credential；“对服务器提供秘密”和“网络明文传输”应区分，TLS 不改变验证端需要保密的事实。密钥轮换、撤销及重放语义均不由 mod-q 自动解决。

**当时建议（历史记录）**：ML-DSA 全神经化、replay、MoE、工具调用与大规模预训练列为本轮非目标。该 replay 建议已被 2026-09-11 后续决策 supersede：后续认证协议必须纳入状态化防重放设计，不作永久排除。

## 10. 建议吸收进下一版方案的改动

1. 提升 G0/P0/P1 优先级，将 P1 设为独立验收里程碑；P2 失败不抹去 P1 已验证结果，但 P1 仍是 P2 的正确性前置。
2. T2 固定 512-update 诊断有界收尾；只处理影响新路线的共性正确性问题，不自动增加从零训练预算。

  二、认证层构造该怎么优化

  2.1 先说当前构造的真实缺陷（不是"参数太小"）

  lwe.py 里 A ~ N(0,1) 实数采样、完全没有 mod q（代码注释自己写了"不做严格的 mod q"）。这不是"toy
  参数强度不够"，而是关系类型错了：

  - m=256, n=128，b = As + e，给定 (A,b) 直接 np.linalg.lstsq 得到 s*，残差是 e 在 col(A) 正交补（维度
    m−n=128）上的投影，‖残差‖ ≈ σ·√128 ≈ 11.3，而 threshold=48。
  - 也就是说伪造不需要"最小二乘攻击研究"，一行 lstsq 就必然通过。C-011 说"可被最小二乘伪造"是准确的，但没说清它是 O(1)
    行代码、必然成功。

  这就是为什么"优化构造"的第一步不是调 n/σ/threshold —— 调任何参数都不改变 lstsq 必然成功。

  2.2 最小、可证明、可落地的升级：加 mod q，并选一个小模数

  我建议的具体构造（这是我认为性价比最高的一条建议）：

  A ∈ Z_q^{m×n} 均匀采样，s 小范数，b = (As + e) mod q
  验证：r = centered_lift((b − As) mod q)，判 ‖r‖_∞ ≤ β

  mod q 一加进去，实数线性结构被破坏，伪造就从 lstsq 变成 search-LWE / BDD 实例。这是 C-011 唯一实质性的升级路径。

  神经化的难点是 mod q 和 centered lift 必须精确，浮点近似会直接毁掉判定。这里有一个具体的参数选择建议：

  - 不要沿用 q = 8380417 ≈ 2^23（Dilithium 模数）。累加上界 ≈ n·q·B_s = 128·2^23·2 ≈ 2^31，超过 float32 的 24 位尾数 →
    GPU 上必须 float64 或 int64，和业务模型的 bf16/autocast 混在一起会很脏。
  - 改用 Kyber 风格小模数 q = 3329。取 n=256, m=512, s ∈ {−2..2}：累加上界 = 256·3328·2 ≈ 2^20.7 < 2^24，整条验证链在
    float32 上逐项精确可表示，可以给出严格的"无舍入"证明，而不是误差界。
  - x mod q = x − q·floor(x/q)，输入是整数时 floor 在整数格点上精确；floor / 比较 / 逻辑组合都能用 ReLU
    组合精确实现在有界整数域上。这样"神经算术精确性"是一个可证明的定理，不是测试观测 —— 这正是 RESEARCH_DESIGN.md §4
    要求的那种义务。
  - 安全强度必须跑 lattice-estimator 给 concrete bit-security，不要自己断言。n=256/q=3329 大致是 Kyber-512
    量级的参数空间，但 plain-LWE + 你的具体 σ 和 β 不能直接套 Kyber 的结论。

  2.3 一个重要的顺带收益：mod-q 构造只和"硬路由"兼容，而新主线正好放弃了端到端训练

  现在 AuthorizationCoordinator 在 training 模式下用 sigmoid((threshold − error_norm)/T) 做软门控，FeatureGate 做
  features * gate_signal。软门控存在的唯一理由是端到端训练时要让梯度回传浅层网络。

  mod-q + centered lift + ‖·‖_∞ 判定是彻底不连续的，软门控在数学上失去意义。但新主线是"冻结骨干 + 只训 public readout +
  硬路由"，本来就不需要梯度穿过 Gate。

  所以这两件事是互相解锁的：放弃端到端训练，才有资格上密码学上更强的门；上了更强的门，就永久回不去端到端训练。这一点应该
  在方案里写成显式的、不可逆的架构决策，而不是留一句"软门控降为消融" —— 软门控消融在 mod-q 下根本跑不起来。

  2.4 明确应该"不做"的三件事

  1. 不要追求 ML-DSA 全神经化。完整 verify 需要 SHAKE-256、NTT、拒绝采样、位打包解析，量级是 10⁵–10⁶
     次模乘加哈希。Shamir 的 AES-DNN 之所以成立，是因为 AES 是固定字节代换 + 线性层、可以用 ReLU
     精确实现查表；签名验证的哈希和解析部分没有这个结构。诚实的目标是"模算术核心可精确神经化 +
     非神经部分显式披露"，09-09 方案 §8 已经有这个意思，但我建议把它从"披露"升级为贡献边界的正面陈述：论文卖点是"哪些密
     码算子可以精确编译进计算图、哪些不能，以及边界在哪"，这比"我们神经化了签名"更站得住、也更不会被审稿人一刀砍掉。
  2. **历史建议（已被后续决策 supersede）**：当时认为无状态前馈层不承担 replay，建议把 replay 从当前实现中暂缓；现行路线保留该边界，但要求在后续状态化授权里实现并验收 nonce/request binding、一次性消费、撤销和并发原子性。
  3. 不要把"credential 是秘密向量 s 本身"这件事说成签名。每次请求都把 s
     明文交给模型，任何观测到一次合法请求的人永久获得凭证。mod-q 升级解决的是"没有 s 的人难以伪造"，不解决"s
     泄露后怎么办"。这两句话要分开写。

  三、怎么给预训练模型插认证层（你的第三个问题）

  3.1 "按开源代码重训一个带 Gate 的新模型"应当明确排除，而不是"暂缓"

  不是优先级问题，是硬件上不可行。0.5B × Qwen2.5 量级语料（~18T tokens）按 6ND 估算约 5×10²² FLOPs；单张 RTX A4000
  以乐观有效算力估，百年量级。即便只用 1/100 语料也是年量级，而且 E2/T2 已经用实验说明了小规模从零训练拿不到语义泛化。

  所以唯一可行路线是：冻结预训练骨干 + 在完整 block 边界插 Gate + 只新增可训练的 public
  readout。这也正好是项目最初设想（浅层公开、深层受控）的自然映射，架构符合度不降。

  3.2 插入方式的核心要求：合法路径必须是"结构恒等"，不是"数值恰好相等"

  CIFAR 里 valid 时 features * 1.0 在浮点上确实精确，所以能过。但不要把这个模式平移到 transformer。建议：

  - Gate 只产出布尔路由 + 索引，forward 里不对 hidden state 做任何算术。合法路径靠 index_select 分组后直接进
    suffix，gate_signal 的乘法彻底移除。这样"恒等"是代码结构上的，不依赖浮点巧合，也不受 autocast 影响。
  - 09-09 方案 §3.2.4 "先分组再执行 suffix，禁止全批深层前向后遮挡" 是对的，而且这条比它看起来更重要 ——
    它同时是零调用证据的唯一成立条件。

  3.3 实现前就该知道的具体陷阱（我认为 09-09 方案漏掉或说得太轻的部分）

  1. tied embeddings。Qwen2.5 小档位的 config 里 tie_word_embeddings 是 true（实现前用 config.json 核对）。这意味着
     lm_head.weight 和 embed_tokens.weight 是同一个 tensor。如果 public head 用 copy.deepcopy(lm_head)
     之外的任何共享引用方式，训练 public head 会直接改 embedding → 污染完整路径，而且 P1
     的等价性测试已经跑完、不会再抓到它。必须：clone 出独立权重、把原 embedding 显式
     requires_grad_(False)、并在训练后重跑一次 P1 等价性作为回归。
  2. 截断 + 原 final norm + 原 lm_head 的"无训练基线"会输出乱码，这是预期结果。原 RMSNorm
     是针对最后一层表示尺度校准的。这个基线应该作为 negative baseline 记录，不要当成 bug 去修，也不要因此判断 cut
     位置选错了。public 路径需要自己的 norm。
  3. 分组后 position_ids / attention_mask / RoPE 必须跟着重排。这是最容易产生"看起来像 Gate 错误、其实是适配错误"的地方
     —— 09-09 方案 §4.5 要求区分适配错误和 Gate 错误，这条是它最主要的具体来源。
  4. 两条路径的 KV-cache 长度不同（public 只有 prefix 层），不能共用同一个 Cache 对象；DynamicCache
     的层数假设会静默错位。
  5. credential 的输入通道。不能走 prompt token（09-09 已要求），但要落地就得注意 HF 的 prepare_inputs_for_generation
     会丢弃未知 kwargs，generate() 直接透传 credential 是不行的，需要重写该方法或干脆自己写解码循环。首轮建议自己写
     greedy 循环，比改 generate 更可控，也更容易做逐 token 对照。
  6. 等价性验收的正确姿势：bf16 下 batch 组成变化会改变 reduction 顺序，logits 逐比特不等是正常的。所以严格 allclose
     只能在 batch=1 + 固定 dtype + 无 KV-cache 的参考配置下做；mixed batch 只能验 greedy token IDs
     一致。这条如果不预先冻结，P1 一定会误报失败并诱发"放宽容差"，那就毁掉整个证据链。09-09 方案 §4.4
     提了，我建议把它提升为冻结前置项：容差和配置在跑第一次实验之前写进 freeze。

  3.4 P1 的价值被低估了

  我想强调一点：P1（插入 + 不训练 + 前后对照）是当前整个项目性价比最高的一步。它不需要训练、不需要数据协议、不需要冻结效
  用门槛，单卡一两天能做完，产出的证据是"Gate 位于一个真实有能力的模型计算图中间，合法路径逐 token 不变，未授权路径
  suffix 零调用"。

  这一步直接把项目从"toy 模型上的路由"抬到"真实模型上的路由"，而且它绕开了压垮 E2/T2 的那个问题（模型会不会做任务 ——
  现在这是预训练模型的既有能力，不是你要证明的东西）。09-09 方案把它放在 P1
  是对的，但我建议把它单独作为一个可发布的里程碑，而不是 P2 的前置步骤。P2 失败不影响 P1 的证据成立。

  即使 P0–P3 全部成功、G1 的 mod-q 核心也成功，项目仍然不能主张白盒抗性（C-009 是已确立的局限）。那么面向安全会议投稿时，第一个问题必然是：

  ▎ 为什么不用外部 verifier + 外部路由？那更简单、也更安全。

  09-09 方案 §7 把"外部 verifier + 相同 dispatcher"列为对照、并单独说明 prefix
  节省，这个方向是对的，但我认为光靠延迟收益撑不住一篇安全论文。真正站得住的论证只有一条：

  能力分级本身是产品需求，不是安全需求。 共享前缀让"拒绝"不等于"什么都不给" ——
  未授权请求仍然获得一个可用的公共服务，而这个公共服务复用了已经发生的前缀计算。外部 verifier 做不到这一点（它要么放行要么拒绝，要么得跑第二个模型）。

  所以我建议论文定位调成 "credential-conditioned capability tiering with in-graph verification"，安全性放在 limitation 章节诚实处理，投
  ML/系统方向而不是纯安全方向。如果坚持安全方向定位，那么 §7 的对照表里必须补一项："外部 verifier + 两个独立模型"的存储/显存/延迟成本，用它来量化 in-graph
  方案省下的是什么。这个对照现在缺，而它是唯一能量化 in-graph 优势的实验。
